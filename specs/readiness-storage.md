## Image acceptance contract

Proofs and QR uploads share one validator/sanitizer. It detects JPEG/PNG/WebP from bytes, rejects mismatched kinds and malformed containers with `422 MALFORMED_IMAGE`, rejects animation or unsupported encodings with `422 UNSUPPORTED_IMAGE_FORMAT`, and rejects excessive dimensions with `422 IMAGE_DIMENSIONS_TOO_LARGE`. Proof files retain the 10 MiB limit and QR files the 5 MiB limit. The request middleware bounds multipart input before parsing. Both image dimensions must be positive and at most **8192**; total declared pixels must be at most **16,000,000**. At most **4096** segments/chunks are parsed.

Supported JPEG is static eight-bit baseline/extended-sequential/progressive DCT with a frame, quantization/Huffman tables, scans and a real end marker. Lengths, component/table references and scan headers are checked. There is no recovery by skipping stray bytes or inventing an end marker. Private APP segments/comments are discarded; JFIF thumbnails are removed; segmented ICC profiles and the Adobe color-transform flag remain.

PNG requires a valid header, supported color/depth, correctly ordered image/palette data, a zlib header, CRCs on every parsed chunk and a real end chunk. Unknown critical chunks and APNG are rejected. Metadata and unknown ancillary chunks are discarded; whitelisted color/rendering chunks are checked and retained. WebP requires a complete RIFF container, valid chunk boundaries/padding, one static VP8/VP8L frame and consistent canvas/feature declarations. Alpha and color data remain; animation is rejected. Trailing bytes outside the validated image container are dropped for all three formats.

These checks use the [W3C PNG specification](https://www.w3.org/TR/png-3/), [official WebP container specification](https://developers.google.com/speed/webp/docs/riff_container), and [JPEG T.81 specification](https://www.w3.org/Graphics/JPEG/itu-t81.pdf). The implementation is a bounded container parser, **not a pixel decoder/re-encoder**. It does not validate compressed entropy, decompress PNG/ICC payloads, or guarantee every accepted bitstream can render. ICC profile contents remain unchanged and can contain profile descriptions; information encoded in image pixels is outside metadata stripping. README now states these limits instead of promising complete metadata removal for every malformed input.

Only a valid, bounded IFD0 orientation value is recovered from EXIF and rebuilt into a minimal TIFF directory. GPS, camera fields, subdirectories and thumbnails are never copied. Orientation 1 needs no retained tag. Malformed discarded metadata cannot cause the original bytes to escape validation. Browser checks compare decoded dimensions and pixel hashes before/after stripping. Chromium honors the JPEG orientation fixture; it ignores WebP EXIF orientation in that fixture, and the rebuilt image retains the same original appearance and orientation tag. Other browsers/devices and accessibility/PWA upgrade behavior remain G08 work.

No native decoder, image service or new runtime dependency was added. Tiny baseline/progressive JPEG and lossless WebP fixtures were generated once using the installed development tool; tests consume the committed fixture bytes and do not require that generator. A 9,554,049-byte adversarial PNG with a large discarded ancillary chunk sanitizes to 111,083 bytes in local Node; the final three runs measured **45.68 / 45.22 / 46.80 ms**. This is not Workers CPU or memory evidence. Actual request parsing, concurrent uploads, CPU/memory and intended-plan headroom must pass G07 before release; no plan or CPU-limit change was made here.

## Durable upload lifecycle

Migration **0014_storage_uploads.sql** follows 0013. It adds upload ownership, upload/deletion claim tokens, a random put-completion identity, lease, retry state, safe error codes, cleanup counters, QR removal checkpoints and two scan cursors. Existing proof/current-QR references are adopted as attached records without deleting objects or changing history. Fresh demo setup separately adopts its references because demo seeding runs after migrations.

Before R2 put, an upload intent and **five-minute** lease commit to D1. A lost intent-insert response starts no R2 operation. After successful put, the writer records a unique completion identity. Proof state/effects and object attachment then commit in the same batch, guarded by staged ownership and the live lease. QR setting, audit, attachment and retirement of the actual previous key also commit together. The previous QR key is read inside the transaction, so overlapping replacements cannot overlook an intermediate winner. QR removal records its operation, clears the setting, audits and schedules retirement in one transaction.

Successful attachment requires R2 put acceptance. [Cloudflare's R2 API contract](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/) describes successful put/delete visibility and bounded, cursor-based listing. D1 and R2 remain separate systems: there is no cross-service transaction. Failure recovery first fences the staged intent in D1 with a conditional reference check; it never decides to delete from a standalone absence read. A committed proof or current QR reference prevents a deletion claim. If a commit response is lost, a proof reference or the QR operation's audit/checkpoint can recover success; unavailable verification leaves durable state for the next pass.

Cleanup owns a new random **60-second** lease before R2 deletion and conditionally acknowledges its matching claim and put-completion identity. A late put cannot attach after cleanup wins ownership. If it finishes during an older deletion, its new completion identity invalidates that deletion's acknowledgement; recovery deletes the unreferenced file again. If it finishes after deletion, its intent is requeued. A remotely late put with a lost response is still covered by a retained tombstone, which is rechecked/redeleted daily. Deleted means the last acknowledged deletion, not a promise that an unknown outstanding write can never arrive.

R2 delete failures back off; after **eight consecutive attempts** the item becomes needs_review with a safe error code. Successful deletion resets the failure counter. A lost cleanup acknowledgement leaves its lease to expire and retry idempotently. A sweep restores reference-backed retention for at most eight records and performs at most **eight** cleanup claims. Retired QR objects have a **one-minute** grace period, longer than the settings cache; proof objects with any retained proof row are protected regardless of booking/proof status. Attached records without references become eligible after their daily check; normal user actions do not purge booking proof history.

Upload records, daily tombstones and QR operation history currently have no automatic pruning. Their retention policy remains L01 work. Do not prune ownership/checkpoints while any late outcome is unresolved. Recheck volume, backlog age, D1 queries/rows and R2 operations at realistic accumulated history under M08/G07. New successful uploads add two transactional round trips and an attachment statement; cleanup and optional scans add bounded background work. Admin health summaries still count over retained history and need measured growth evidence.

## Historical discovery and operator visibility

Managed-intent cleanup runs from cron. `STORAGE_CLEANUP_ENABLED=false` pauses both request cleanup and scheduled deletion/discovery; failure checkpoints still persist. **Historical orphan discovery is disabled by default.** Only `STORAGE_ORPHAN_SCAN_ENABLED=true` enables it after a reviewed inventory/retention decision. It scans one leased page of at most eight objects per pass, alternating the fixed `proofs/` and `settings/gcash-qr/` prefixes with persisted cursors. Objects younger than 24 hours are preserved. Older objects without a proof/current-QR reference or known upload intent receive a durable cleanup record. Adoption and cursor advancement commit together; losing a response cannot skip an unregistered page. Unknown prefixes are never scanned or deleted; unreferenced tracked keys outside the expected namespace require review.

Settings → Upload recovery shows expired uploads, pending cleanup, deletion retries, manual review and oldest pending age. `GET /api/admin/storage-health` remains admin-only and returns counts without keys, filenames, owners or content. Cleanup failures retain fixed codes; logs identify only upload IDs and deferred work. An item needing review requires an operator to inspect evidence and repair/requeue through the controlled procedure; there is no blind resend or delete button.

Run [scripts/storage-inventory.sql](../scripts/storage-inventory.sql) read-only on a 0014-upgraded authorized copy. Review untracked references, deletion-state references, expired/invalid claims and manual review. Also compare the actual bucket to D1 using read-only R2 list/head checks; SQL alone cannot prove every referenced object exists. Existing missing objects require an approved restore/repair decision, never invented proof bytes.

## Rollout, rollback and recovery procedure

1. Rehearse fresh and populated 0013→0014 upgrades, backup and restore on isolated resources. Record original reference/object inventories and the accepted historical retention policy. The migration keeps existing records and creates no remote storage actions.
2. **Pause proof/QR uploads and drain old invocations before applying 0014 and switching Workers.** Old writers do not respect staged/deletion ownership. Keep legacy discovery disabled until only the new writers are active and reference/object inventory is reviewed. New managed recovery must run only on the migrated schema.
3. Verify synthetic proof/QR acceptance, malformed rejection, concurrent replacements, ambiguous outcomes and cleanup on intended D1/R2/runtime. Enable historical discovery only after owner approval and monitor backlog/queue age, deletion errors and privacy/storage impact.
4. Before rollback, stop upload writers, set `STORAGE_CLEANUP_ENABLED=false`, and drain active operations. Keep additive tables/checkpoints. Returning to the old untracked writer while new cleanup is active can create deletion races; rollback is not safe merely because the schema is additive. Reconcile unresolved intents and rehearse an approved forward repair or rollback with a named operator.
5. For needs_review, verify current references, R2 evidence, writer/cleanup activity and the original intent. Preserve referenced files. For an unreferenced object, requeue only after confirming no writer can still legitimately attach it; keep the tombstone/checkpoint until retention is accepted. Audited repairs must retain operation identities. Pause cleanup while restoring references or performing out-of-band repairs.

No production scan, object deletion, remote migration or release was performed here. Historical reconciliation, CPU/memory/quota evidence, independent review and incident/retention ownership remain required to close M10/M11 and G03/G06/G07/G11.
