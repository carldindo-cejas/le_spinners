# Concurrency, reliability, and capacity audit — 8 October 2026

The repaired candidate passed simultaneous booking and payment tests with **50 players**, including same-slot contention and overlapping maintenance. It provides good local evidence for **10, 15, and 20 simultaneous players**, and a successful 50-player burst. Production readiness remains conditional on the deployment requirements below. No saturation threshold or production capacity ceiling was established.

The original candidate was not ready: when 10/15/20/50 players requested different free slots together, only one booking succeeded in each wave. A facility-wide revision rejected every other request despite their slots remaining free. A separate stale-payment-review race could approve or reject a replacement screenshot that staff had never reviewed. Both were repaired without removing atomic overlap, credit, or state checks.

At audit completion, changes were local and had not been deployed. The user subsequently authorized production migration and deployment; migrations 0017–0019 and the candidate were deployed successfully, as recorded in the [deployment record](deployment-concurrency-2026-10-08.md). Tests used synthetic accounts and disposable local databases/buckets. The audit did not inspect the deployed account's plan or contact a payment/email provider; the later rollout used separate read-only production preflight and live checks.

It completed **2,425 measured requests**, with **52 requests outstanding at once**: 50 player requests plus a staff dashboard request and a scheduled invocation. These are concurrent requests launched by the client; D1 serializes SQL execution. Fifty concurrent sign-in flows included actual salt lookup, client password derivation, and session creation; password derivation can stagger login POST arrival.

Four complete workflows created a paid booking, uploaded/approved proof, cancelled through a disruption, replayed that disruption, issued credit, submitted two concurrent same-key refunds, and created/released a credit-backed replacement. **Flow and existing preventive controls**

The player booking screen (`public/js/player/screens/book.js`) treats availability as a preview. It removes lost selections after refresh and shows conflict alternatives when submission loses. `core/booking-request.js` retains a request identity and payload across ambiguous network failures. The staff console uses the same durable booking-operation mechanism. Pending submissions remain disabled; view lifecycle guards prevent stale or signed-out requests from repainting a new view.

`routes/bookings.ts` authorizes the session and validates input before `createHold` in `lib/bookings.ts`. `checkSlots` checks dates, opening hours, resources, closures, and requested segments. The final `INSERT … SELECT … WHERE` independently checks **all resource intervals, player intervals, effective expiry, and the cap of two TEMPORARY holds** against current D1 data. Rejected resubmit windows and submitted payments are excluded from that cap. Requested gaps are represented by actual segments, so adjacent or gapped bookings remain possible. Booking, slot rows, credit ledger changes, operation identity, and guarded effects commit in one D1 batch. A refused insert creates no success effects; a failed statement rolls back the batch. This relies on [D1's transactional batch semantics](https://developers.cloudflare.com/d1/worker-api/d1-database/).

The partial unique index on `(resource_id,date,start_min)` is an additional exact-start backstop. It is **not a general interval exclusion constraint**. Interval safety comes from the conditional statement and transactional write protocol, with the index as backup. Every future writer must use that protocol; arbitrary direct SQL can bypass general overlap prevention.

Session loading joins the current account and checks `auth_version`, expiry, active state, and role. Auth rate counters use atomic database updates; fifty existing accounts behind one IP signed in successfully. CSRF origin checks, ownership checks, staff/admin authorization, response allowlists, private proof storage, signed URLs, and image size/structure checks remain in place. Account-state/password revocation tests exercise delayed requests and separate runtimes.

Proof submission stages the R2 object under a durable lease, then conditionally changes the booking and attaches the proof in one database batch. R2 and D1 are separate systems; upload leases and reconciliation recover their partial failures. Approvals/rejections require the submitted proof identity at the HTTP boundary. Booking transition tokens guard ordinary booking effects, notices, and credit release; deferred disruptions use schedule revisions and guarded item outcomes/statuses. A duplicate proof or decision receives a predictable state conflict rather than another payment/approval event.

Player cancellation of a confirmed booking is deliberately refused. Unpaid release is conditional; confirmed cancellation and credit issuance use the staff disruption API, revision-checked previews, and durable replay identities. Credit balances have nonnegative CHECK constraints and ledger recomputation; unique issuance/release identities and refund-operation records prevent duplicate financial effects. Automatic retries were not added to arbitrary mutations. Financial and booking recovery reads the committed identity before replaying an intent.

Cron uses the same conditional transitions and bounds each maintenance task to eight rows. Lazy maintenance is throttled per isolate. Outbox delivery has durable claims, immutable provider idempotency payloads, bounded attempts/timeouts, and review states for ambiguous or exhausted delivery. These controls protect correctness; their throughput limits are findings below.

**Findings repaired**

No Critical defect was demonstrated. The following are newly reproduced defects and their implemented corrections. Worker paths are under `src/worker/`; frontend paths are under `public/js/`.

|---|---|---|

**Database and capacity recommendations**

D1 processes one database's queries sequentially and can return overload errors when its queue fills; throughput depends on query duration and statements per request. The 50-player localhost burst is not an estimate of production requests/second. Current code does not use D1 Sessions/read replicas for decisions: normal database calls go to the primary. If adding replication, preserve primary or bookmark consistency for authentication, inventory, and mutation planning. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [database API](https://developers.cloudflare.com/d1/worker-api/d1-database/).

Availability uses a four-statement batch, rather than a query per cell; it builds the grid in memory over a bounded booking window. Existing indexes cover resource/date/start lookup, maintenance eligibility, user/date lists, message cursors, credits, sessions, and outbox/storage checkpoints. `EXPLAIN QUERY PLAN` confirmed the UNIQUE R2-key index already supplies the proof-reference cleanup lookup; no redundant index was added. Payment function measurements were 13 statements for submission/resubmission, 13 for rejection, and eight for approval, excluding route/auth/detail reads and extra alert recipients.

Preserve the transactional batches, nonnegative ledger checks, partial unique indexes, and configuration/transition guards. Apply migrations **0017–0019** in order before publishing code that reads the new revision tables. Run resource-name preflight first and reconcile every physical resource mapping; different names can still refer to one physical court. If multiple independent writers are introduced, add a database occupancy/exclusion design after auditing historical data; the existing exact-start index alone is insufficient.

Instrument deployed CPU, SQL duration/rows read/written, mutation p95/p99, overload/429/409/5xx rates, task failures, and queue age. Cloudflare retries qualifying read-only D1 queries; any additional application retry should be bounded/jittered and limited to safe reads or durable mutation replay, not an arbitrary repeat of financial effects. [D1 retry guidance](https://developers.cloudflare.com/d1/best-practices/retry-queries/).

**Conditions before production use**

The candidate is locally suitable for 10+ concurrent existing players; 15 and 20 are directly supported by simultaneous-write evidence, and 50 passed the tested bursts. Production approval needs migrations/preflight, verified physical inventory, the intended plan/query budget, and a longer mixed staging soak with realistic history, recipient fan-out, network latency, uploads, and multiple isolates. Capture actual deployed CPU/memory and D1 usage, test provider/R2 failures and ambiguous-response recovery, and confirm staff payment reconciliation.

Deploy the updated API and frontend together: old cached staff clients omit the now-required `proofId` and receive 422 until refreshed. The service-worker version is bumped; verify update behavior on actual phones. Complete the existing business/device/backup/operational gates in the other readiness reports. This audit does not close those gates or certify a 50-player production SLA.
