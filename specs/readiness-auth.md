# M01 credential and session versioning

Implemented locally by Codex, October 7, 2026; M01 is In review. Independent reviewer and staging/recovery operator remain unassigned. No deployment, remote provisioning/reset, production credential change or normal development database reset was performed.

## Version and session contract

Migration **0015_auth_versions.sql** adds `users.auth_version`, an opaque winning-change identity and `sessions.auth_version`. Existing credentials remain unchanged and existing sessions receive the account's initial version. A database AFTER UPDATE trigger advances the version whenever password hash/salt/iterations/scheme, role or status actually changes. Unrelated profile edits do not advance it. The trigger covers direct operational updates and administrative resets as well as application writes; its inner update touches only the version, so it does not recurse on the credential columns. A session INSERT trigger rejects unversioned, stale or disabled-account inserts.

Login verifies credentials as before, then conditionally inserts a session only while the verified password hash, account version, role and active status still match. A rejected insertion returns `401 INVALID_CREDENTIALS` and sets no cookie. Successful creation and deletion of any previously loaded browser session share a D1 batch. A stale failed login therefore cannot destroy a still-valid previous session. Cookie lifetime, HttpOnly/SameSite/Secure behavior, player sliding expiry and fixed staff/admin lifetime remain in place.

Every session load checks active status, expiry and equality of stored session/account versions. The safe user DTO contains neither version nor winning-change identity. Delayed player activity updates also compare versions, so an older request cannot overwrite expiry after a password change has promoted the initiating session. Disabled then re-enabled accounts and changed roles require fresh authentication; an old session never regains access merely because the status or role returns to its original value.

A password change uses compare-and-swap on the verified account version/hash, loaded session version and its still-live session row. Its conditional account update, promotion of that **same initiating session**, deletion of all other sessions and winning audit record commit together. Dependent statements require a fresh random change identity plus the resulting version; a losing concurrent request cannot adopt another winner or create a second audit, including identical new-password payloads. A losing request returns `409 CREDENTIALS_CHANGED` and asks the user to sign in again. Keeping the initiating cookie avoids changing its browser persistence choice or extending a staff session's expiry.

These transactional guarantees use [D1 batch semantics](https://developers.cloudflare.com/d1/worker-api/d1-database/) and the [SQLite trigger contract](https://www.sqlite.org/lang_createtrigger.html). Versions revoke subsequent session loads and stale credential writes. They do not cancel an unrelated request that already passed authentication before revocation; stronger fencing of every privileged business mutation would be a separate protocol. M02–M04 browser logout/navigation/lifecycle gaps remain open.

## Administrative provisioning and recovery

`scripts/create-admin.mjs` requires schema 0015. It reads only the existing account ID/version, then generates a conditional create/reset with `scripts/lib/admin-account.mjs`. New-account mode does not overwrite an account that appeared concurrently. Reset mode updates only the expected account/version and assigns a unique change identity; session cleanup and the final applied count refer to that identity. A concurrent password/role/status change makes provisioning fail visibly without a losing reset deleting the winner's sessions. The credential-change trigger revokes older sessions even if later physical deletion fails or the CLI's statements are interrupted.

The CLI invokes the installed Wrangler through Node with structured arguments and no shell. Password, pepper and client proof remain hidden inputs; only the credential HMAC is written to the existing protected temporary SQL file, which is removed in `finally`. Credential-bearing CLI output is captured rather than echoed, including failures. A database/schema failure produces a fixed operator message. The command reports success only when its final applied check confirms the operation. No remote command was executed during this implementation. Controlled identity verification, account recovery policy and deployed pepper/migration-history evidence remain I01/I02 work.

Raw changes to auth-version fields or restoring older credential/session snapshots are privileged operations outside this contract. Operators must preserve monotonic versions or explicitly revoke sessions as part of a reviewed repair. Do not reinsert stale token hashes as current sessions.

## Migration and rollout procedure

1. Inspect migration history and redacted account/session counts on an authorized copy, including I01's historical 0002 applicability. Back up and rehearse populated 0014→0015 and restoration. This migration does not reset passwords or infer which pre-upgrade sessions resulted from the old race.
2. Decide whether preserving existing sessions is appropriate or whether a reviewed all-session revocation is needed for historical uncertainty. Record the operator, scope and customer/recovery impact; no global revocation was performed here.
3. Pause authentication/credential and relevant authenticated writers, drain old invocations, apply 0015 and activate the new Worker/provisioning script together. Old session creators omit the new version and will fail the INSERT guard; old access middleware does not enforce version revocation. Mixed old/new writers are not a safe rollout.
4. Verify all three portals, retained/other-session behavior, delayed old login, resets, disable/re-enable, role transitions and cross-isolate overlap on intended D1/runtime. Reopen traffic only after evidence identifies the exact candidate and schema.
5. Prefer a reviewed forward repair. Before rollback or restoring credentials/sessions, stop and drain writers and review session revocation and the insertion guard. Reverting code alone neither removes the additive schema nor preserves the new security guarantee. Rehearse the chosen recovery with a named operator; never drop safeguards or restore old sessions blindly.

Run [scripts/auth-inventory.sql](../scripts/auth-inventory.sql) read-only on schema 0015. Invalid/unversioned/ahead-of-account counts require review. Retained older-version/disabled session rows are informational: access rejects them before physical expiry cleanup, and their existence does not mean revocation failed. Keep credential values, cookie tokens/token hashes, client proofs and customer identities out of tracker artifacts.
